## 2. Учасники

- **5 людей** — якісна перевірка (за рекомендацією `after-hours-redesign` «5 якісних usability-сесій»); це не статистична вибірка, A/B-висновків не робити.
- Профіль (assumption — уточнити за [overview](../overview.md)): читає AI-новини щонайменше раз на тиждень; користується телефоном і десктопом. Змішати: 3 на mobile (390 px), 2 на desktop; мінімум 1 читає українською, 1 англійською; мінімум 1 користується клавіатурою/screen reader або збільшеним шрифтом браузера.
- Не залучати тих, хто бачив прототип. Без винагород, що впливають на відповіді. Не збирати PII; запис — з усною згодою, імена в нотатках замінити на P1–P5.

## 3. Що показувати

- Середовище A — **production-like preview** гілки після міграції токенів (`/en/news`, `/en/digests`, story).
- Середовище B (порівняння, за бажанням) — поточний production. Порядок міняти між учасниками.
- Не пояснювати, де що знаходиться. Модератор мовчить після задачі; підказка = «rescue» і фіксується.

## 4. Задачі (з аудиту §7) і що фіксувати

Кожна задача: формулювання учаснику → успіх без rescue / з rescue / провал → час → цитата.

| # | Задача для учасника | Успіх, якщо | Ціль |
|---|---|---|---|
| T1 | «Покажіть, як би ви відфільтрували або відсортували новини» | Знаходить filter і sort | ≤ 10 с |
| T2 | «Знайдіть матеріали про Agents & MCP за останні 7 днів» | Категорія + період застосовані | без rescue |
| T3 | «Додайте ще один topic/tool. Що зараз показано?» | Правильно пояснює, як поєднались filters | без rescue |
| T4 | «Скиньте один filter, потім усі» | Розрізняє remove one / Clear all | без rescue |
| T5 | «Перейдіть на 2-гу сторінку, відкрийте матеріал, поверніться назад» | Повертається в той самий state | 0 втрат state |
| T6 | «Скопіюйте адресу, відкрийте в новій вкладці» (модератор робить reload) | Той самий result set | 0 втрат state |
| T7 | «Поясніть, чим відрізняються Newest, Relevance та Most engaged» (після змін — за фактичними назвами) | Пояснення відповідає реальній поведінці | без хибних припущень |
| T8 | T2 → T4 лише з клавіатури на mobile drawer (screen reader / Switch Control за можливості) | Виконано без миші | без rescue |

Додатково фіксувати: чи вважає учасник «Hot topics» активними filters (ціль — 0 випадків, якщо це лише навігація). Після задач: SUS-lite (3 запитання, шкала 1–5): «було легко знайти потрібне», «завжди розумів, що зараз відфільтровано», «повернувся б сюди».

## 5. Пороги рішення

Discovery-цілі з аудиту (не виміряні показники):

- ≥ **80%** виконання задач без rescue по всіх 5 учасниках (тобто ≥ 32 з 40 спроб T1–T8);
- **0** випадків, коли Hot topics прийнято за активні filters;
- **0** втрат state після Back / Forward / reload.

Правила: будь-яка проблема, що заблокувала задачу у ≥ 2 учасників, — **blocker**: виправити до broad rollout. Проблема в 1 учасника — у backlog із severity. При провалі порогів: не розгортати, виправити, повторити з 3 новими учасниками лише проблемні задачі.

Severity: **S0** — задачу неможливо виконати; **S1** — виконав із rescue або > 2× повільніше цілі; **S2** — помітив, але не заважає; **S3** — побажання.

## 6. Обґрунтування вибору методу (assumption)

5 сесій виявляє більшість проблем зі структурою discovery (класичне евристичне правило Нільсена — не перевірялось на цій аудиторії). Малий трафік сайту не дозволяє статистичного A/B, тому вимірювання після запуску — за [after-hours-redesign](../product/after-hours-redesign.md) «Оцінка після запуску».
