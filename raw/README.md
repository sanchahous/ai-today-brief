# raw/ — незмінні вхідні дані

> ⛔ **Нічого тут не редагувати, не перейменовувати, не «причісувати», не видаляти.**
> Це доказова база. Виправлення й інтерпретації живуть у `wiki/`, з посиланням на сирий файл.

Агент читає цю зону, але ніколи в неї не пише сам — окрім збереження виходу MCP-скрапера
(`raw/scrapes/`), і навіть тоді файл лягає як є, без правок.

## Структура

| Папка | Що сюди | Приклад імені |
|---|---|---|
| `exports/` | Викачки з аналітики й SEO-інструментів: GA4, GSC, Ahrefs, Beehiiv | `2026-08-02-gsc-queries.csv` |
| `research/` | PDF, воршкопи, ресерч-звіти, знімки сторінок конкурентів, транскрипти | `2026-07-25-workshop-prompts.pdf` |
| `scrapes/` | Вихід Apify та інших скраперів — сирий JSON | `2026-08-02-tldr-landing.json` |
| `db/` | SQL-дампи, знімки схеми, експорти таблиць | `2025-mvp-migration.sql` |
| `reference/` | Незмінні референси: дизайн-прототипи, чужі специфікації | `prototypes/` |
| `_local/` | **git-ignored.** Bulk-медіа, великі дампи, будь-що з PII або ліцензійними обмеженнями | — |

## Іменування

`YYYY-MM-DD-{коротка-назва}.{ext}` — дата йде першою, бо у сирих даних головне «коли зняли».
Якщо джерело саме має дату (звіт за червень, знятий у липні) — дата **зняття** в імені,
дата **покриття** в summary-сторінці wiki.

## Що робити після додавання файлу

Сказати агенту «оброби» — далі йде
[ingest workflow](../wiki/architecture/agentic-workflow.md#ingest): повне прочитання → 3–5
інсайтів на підтвердження → summary-сторінка у `wiki/` → оновлення концепт-сторінок →
`wiki/index.md` → `wiki/log.md`.

## Що НЕ кладемо сюди

- Згенеровані нами деліверабли → `artifacts/`.
- Наші висновки й аналіз → `wiki/`.
- Продуктовий код → `src/`, `pipeline/`, `supabase/`.
- Секрети, токени, `.env` будь-якого виду → **ніде в репозиторії**.
